# FEAT-050: The inboxes filter by domain tab and one popover

## Problem
The seller and admin message inboxes each render two rows of pill chips for `?filter=` and `?status=` (`components/seller/messaging/filters.blade.php`, `components/messaging/filter-chips.blade.php`). Five or six kind chips wrap to a second line in the list pane (384px seller, 400px admin), the three status chips sit under them as a third line, and the two rows read as one undifferentiated cloud. The seller header also carries a "New conversation" link and the admin header a total count, neither of which the reader needs before reading the list. The admin lands on `needs-reply`, the seller on `all`; both hide unread threads inside the date order.

## Goal
A message inbox opens on what needs attention and lets the reader narrow it with two controls: a domain tab and one filter popover.

## Outcome
- Both inbox headers are the title "Messages" alone: no count, no "New conversation" link.
- Below the title, a row of underline tabs picks the domain: seller `All · Buyers · Support`, admin `All · Sellers · Customers`. `All` is the default and every tab is a plain link carrying the other current choices.
- At the right end of the tab row, one "Filter" control (funnel icon, the word Filter, and a count when anything differs from the default) opens a popover with two checkbox groups: **Type** (Questions, Orders, Support) and **Status** (Open, Resolved; admin adds Needs reply with its live count). Choices within a group are OR'd; groups are AND'd. The popover has a Reset link (back to the default for the current domain) and a Done submit. It works with no JavaScript.
- The default is every type and Open only, so a fresh inbox shows a plain "Filter" with no count.
- Rows sort unread first, then newest `last_message_at`; the unread dot stays on each unread row. Resolved rows appear only when Resolved is checked.
- Every link and form that carries the pane's choices onward (row links, "Showing N of M", the composer's action and hidden fields, the reply redirect, the "Show all" escape in an empty state) carries the new choices instead of `filter`/`status`.
- Unknown values still answer 400 (docs/alignment.md §5). `docs/messaging.md` § "Inbox filters and the seller's queue" and the `/admin/messages` row of docs/alignment.md §4 describe the new query vocabulary.
- The shop (customer) messages page is unchanged.
- `make precommit` green; `make check` green before the PR.

## Why it matters
A seller or admin opens Messages to answer what is waiting. Two rows of pills put six equal choices in front of that; unread threads hide in the middle of the list; and the controls for looking backwards (resolved, all) sit as peers of the controls for looking forward. One tab row plus one popover leaves the list on top and puts the secondary choices one click away.

## Discovery notes
- Design canvas (accepted): https://claude.ai/code/artifact/014de941-1814-4d83-8677-a2dc21e42ac1 — page 1 holds four frames (seller default, seller filter open, admin default, admin Sellers tab with filter open). Tailwind UI blocks: "Tabs with underline" for the domain row, "Filters — popover" for the popover, checkboxes in the portal's accent (indigo for seller, stone for admin).
- Suggested query shape: `domain=` (seller `all|buyers|support`, admin `all|sellers|customers`), `type[]=` (`questions|orders|support`), `status[]=` (`open|resolved`, admin also `needs-reply`). Absent `type` means every type; absent `status` means `open`. The two `MessagesQueryRequest` classes already own validation and the 400; extend them rather than adding parsing to the controllers.
- Mapping to `ConversationKind`: seller Buyers = `ListingQuestion` + `Fulfillment`, Support = `AdminSeller`; admin Sellers = `AdminSeller`, Customers = `AdminCustomer`. Type Questions = `ListingQuestion`, Orders = `Fulfillment`, Support = the desk kinds (`AdminSeller` for the seller; `AdminSeller` + `AdminCustomer` for the admin). Admin `All` still includes the oversight kinds the way today's `all` does.
- `needs-reply` is a subset of `open`; the existing `needsReply` scope already encodes it. Checking Needs reply alone is the desk's queue; with Open it is just Open.
- Unread-first sort: `withUnreadCountFor` already adds `unread_count`; order by `unread_count > 0` desc, then `last_message_at` desc. The seller's `unansweredFirst` scope only served the `questions` chip and can go if nothing else reads it.
- The seller thread's "Publish as FAQ" (`components/seller/messaging/thread.blade.php:56`) is the existing `<details>`-as-popover idiom; the filter popover can follow it with a `method="GET"` form inside. Checkboxes: Tailwind UI's `size-4 rounded` input in the accent.
- The seller's `filterCounts` (unread and questions chip counts) go away with the chips; the admin's Needs reply hint is one `needsReply()->count()` scoped to the current domain.
- `paneFor` (both controllers) prepends the shown thread when the pane's choices exclude it; the show route's admin default (`paneFilter`/`paneStatus` = `all`) becomes "every status" so a resolved thread still lands in its own pane.
- Tests are Pest sidecars beside the source (`app/Http/Controllers/{Seller,Admin}/MessageControllerTest.php`, `app/Http/Requests/*/MessagesQueryRequestTest.php`, `app/View/Components/ListPaneRowTest.php`); the ones pinned to `?filter=`/`?status=` need rewriting to the new vocabulary, not deleting.
- Node and Rails do not get this in the same change; their inboxes keep `filter`/`status` until a parity ticket. Note it in the alignment doc's PHP row.
